# 밑바닥부터 다시 쌓는 3-Tier 인프라 — DB단 기획·설계 (최종)

지금까지 **네트워크 구축**, **보안 그룹**, **도메인·주소 연결(Route 53·ACM)**, 그리고 **컴퓨팅(ALB·ASG·Docker·ECR)** 까지 진행했다.  
3-Tier 단지에서 아직 비어 있는 마지막 층은 **Database**다.

이 글은 Terraform 구현 코드가 아니라 **기획과 설계의 최종본**이다.  
무엇을 왜 이렇게 두는지, 교육에서 배운 InnoDB Cluster를 우리 VPC에 어떻게 이식하는지,  
그리고 **데이터(자산)를 어떻게 영속·백업할지**까지 도면에 고정한다.  
`modules/database` 코딩은 다음 편이다.

교육 참고: [Backbone Archive — 교육](https://backbone-archive.tistory.com/category/%EA%B5%90%EC%9C%A1)  
특히 **Day31(InnoDB Cluster + Router)**, **Day29(백업·RPO/RTO)** 축을 이 프로젝트에 맞춘다.

## 0. 프롤로그 — 왜 DB인가, 왜 RDS가 아닌가

### 0.1 남은 것은 Database다

| 층 | 우리가 한 일 | 비유 |
|----|--------------|------|
| 네트워크 | VPC, 서브넷 9개, NAT, S3 Endpoint | 단지 도로·담장 |
| 보안 그룹 | sg-alb, sg-app, sg-db, sg-bastion… | 출입증·도어락 |
| 도메인 | NS 위임, ACM, (compute) Alias | 단지 주소·정문 자물쇠 |
| 컴퓨팅 | ALB, ASG, Nginx+Nest, ECR | 로비·주방 |
| **Database** | **← 지금** | **지하 금고 — 장부** |

주방이 열려도 **장부가 없으면** 주문·회원·결제는 성립하지 않는다.  
`/health` 200은 “건물이 섰다”는 뜻이지, “장사가 된다”는 뜻이 아니다.

### 0.2 공부 목적: RDS를 쓰지 않고 직접 구축한다

실무에서는 **RDS(또는 Aurora)** 로 쉽고 빠르게, 그리고 **상대적으로 안전하게** 운영하는 편이 흔하다.  
패치, Multi-AZ, 스냅샷, 엔드포인트 — AWS가 많은 바닥을 가려 준다.

우리는 그 길을 **일부러 가지 않는다.**

> RDS로 관리의 편안함을 사기보다,  
> **EC2 위에 데이터베이스를 직접 올려**  
> “RDS가 대신해 주던 일이 무엇이었는지”를 손에 익힌다.  
> **공부의 목적**을 상기시키기 위해서다.

미리 못 박는다. 앞에서 이야기했듯 우리는 **InnoDB Cluster**로 갈 것이다.

### 0.3 실제 서비스에서는 RDS가 더 중요한 경우가 많다

학습용 선택과 운영용 선택을 **섞지 않는다.**

| 구분 | 이 프로젝트 (학습) | 실제 서비스 (운영) |
|------|-------------------|-------------------|
| DB | EC2 + InnoDB Cluster 직접 구축 | 대개 **RDS / Aurora** 등 관리형 |
| 목적 | 원리 확인 | **고객 데이터 보호·지속 운영** |
| 책임 | 우리가 OS·복제·백업·페일오버를 짐 | AWS + 팀의 운영 절차 |

> **서비스에서 가장 중요한 것은 고객의 데이터다.**  
> **데이터는 곧 자산이다.**

우리가 네트워크 격리, 보안 그룹, Bastion, HTTPS에 그토록 신경을 쓴 이유도 결국 같다.  
화면이 예쁜 것보다, **데이터가 유출·변조·소실되지 않게** 하는 것이 우선이다.

직접 구축은 “RDS를 무시한다”는 뜻이 아니다.  
오히려 나중에 RDS를 켤 때,

- 엔드포인트 뒤에 무엇이 있는지  
- 왜 백업 보존 기간을 묻는지  
- 왜 퍼블릭 액세스를 끄는지  

를 **이해한 채로** 쓰기 위한 훈련이다.

### 0.4 한 문장으로 방향 고정

```text
학습: EC2 × 3 + InnoDB Cluster + Router + EBS 영속 + cron 백업
운영(현실): 고객 자산 보호가 최우선 → 관리형 RDS를 진지하게 검토
이 글: 학습 경로의 설계 SSOT (단일 진실 원천)
```

## 1. 우리가 만들 것 — EC2 위 InnoDB Cluster 3노드

### 1.1 한 대가 아니라 세 대

단일 MySQL 한 대만 올리면 구축은 빠르다.  
하지만 그 한 대가 꺼지는 순간 **장부 방이 통째로 잠긴다.** (SPoF)

그래서 우리는 **데이터베이스를 3개(노드 3대)** 구축한다.

초안으로 말한 역할을 기술 용어에 매핑하면 다음과 같다.

| 초안 표현 | InnoDB Cluster 용어 | 하는 일 |
|-----------|---------------------|---------|
| **읽기/쓰기 하나** | **Primary** (읽기·쓰기) | INSERT/UPDATE/DELETE 등 **쓰기**의 중심. 읽기도 가능 |
| **읽기 둘** | **Secondary × 2** | 복제본. **읽기** 분산·장애 시 승격 후보 |
| “리드 레플리카를 구현” | Group Replication으로 묶인 **멤버** | 클래식 비동기 Read Replica와 **닮은 그림**, 합의 방식은 다름 (아래 §3) |

```text
                    ┌─ Secondary (읽기)  AZ-b
Primary (읽기/쓰기) ─┼─ Secondary (읽기)  AZ-c
       AZ-a         └─ (서로 GR 무전기로 장부 합의)
```

비유:

> 금고 칸이 **세 개**다.  
> **도장을 찍는 주인(Primary)** 은 한 명,  
> **사본 장부를 든 부주인(Secondary)** 이 두 명이다.  
> 주인이 쓰러지면 부주인 중 하나가 도장을 이어받는다.

### 1.2 왜 “리드 레플리카”라고 말해도 되는가 / 어디가 다른가

사람들이 RDS에서 익숙한 **Read Replica** 그림:

```text
Primary ──(비동기 복제)──▶ Replica1
                      └──▶ Replica2
앱 쓰기 → Primary
앱 읽기 → Replica (선택)
```

InnoDB Cluster (Group Replication) 그림:

```text
세 멤버가 그룹으로 합의(쿼럼)
쓰기 확정에 과반 동의 개념이 개입
Router가 RW/RO 포트로 안내
```

| | 전통적 Read Replica 감각 | 우리 InnoDB Cluster |
|--|--------------------------|---------------------|
| 노드 수 | Primary + N replica | **멤버 3 (쿼럼)** |
| 쓰기 | Primary만 | Primary 중심 (싱글 Primary 모드) |
| 읽기 | Replica로 분산 가능 | Secondary / Router RO(`6447`) |
| 페일오버 | 승격·DNS/엔드포인트 정책 | 클러스터 선출 + **Router** |
| 학습 포인트 | 복제 지연 | **복제 + 합의 + 쿼럼** |

초안의 “읽기/쓰기 1 + 읽기 2”는 **운영 그림으로는 정확**하다.  
다만 구현 이름을 “RDS Read Replica 세 개”가 아니라 **InnoDB Cluster 멤버 세 개**로 부른다.  
원리를 확인하려는 목적에는 Cluster 쪽이 RDS가 가리던 바닥을 더 잘 보여 준다.

### 1.3 전체 아키텍처 (단지 안)

```text
[사용자]
   │ https://hdg1234.cloud
   ▼
[ALB] → [앱 EC2: Nginx → Nest]
                    │
                    │ 127.0.0.1:6446  (MySQL Router — 집 안 안내원)
                    ▼
              [Router]
                    │ sg-app → sg-db :13306
                    ▼
     ┌──────────────┼──────────────┐
     ▼              ▼              ▼
  [DB-a]         [DB-b]         [DB-c]
  Primary        Secondary      Secondary
  10.0.20.x      10.0.21.x      10.0.22.x
  AZ-a           AZ-b           AZ-c
     └──── GR :13361 (무전기) ────┘

  데이터: 각 노드 EBS 볼륨 (영속)
  백업: cron → 덤프 → S3 (보존 기간 후 삭제)
```

관리자만의 길:

```text
내 PC → Bastion(SSH) → DB 노드 (SSH / MySQL Shell :33060)
인터넷 → DB 직행  금지
```

## 2. 핵심 비유 — 데이터는 자산, 금고는 세 칸

| 기술 | 비유 | 한 줄 |
|------|------|------|
| 고객 데이터 | **자산·장부** | 서비스의 심장. 유출·소실이 최악 |
| 보안 그룹·프라이빗·Bastion | 경비·도어락·담장 | 자산이 새지 않게 |
| DB EC2 × 3 | 금고 칸 3개 | 한 칸 장애 ≠ 전 자산 소멸(목표) |
| Primary | 도장 찍는 주인 | 읽기/쓰기 |
| Secondary × 2 | 사본 담당 | 읽기 + 승격 후보 |
| Group Replication | 직원 무전기 | 세 칸이 공식 기록을 맞춤 |
| Quorum | 이사회 정족수 | 3중 2 |
| MySQL Router | 안내원 | 앱은 Primary IP를 외우지 않음 |
| EBS 데이터 볼륨 | 철제 캐비닛 | EC2를 꺼도 장부가 디스크에 남음 |
| cron 백업 → S3 | 매일 서류 복사·창고 보관 | 금고 3칸이 동시에 틀린 명령을 받아도 어제본은 남김 |
| 오래된 백업 삭제 | 창고 정리 | 비용·규정에 맞는 보존 기간 |
| RDS (실서비스) | 전문 금고 업체에 위탁 | 자산 보호를 외주에 가깝게 |

> 보안을 신경 쓰는 이유의 상당 부분은  
> **“데이터가 유출되지 않게”** 하기 위해서다.  
> 네트워크·SG·HTTPS는 그 수단이고, DB 설계는 **자산이 어디에 어떻게 사는지**를 정하는 일이다.

## 3. InnoDB Cluster가 하는 일 — 원리

### 3.1 단일 DB의 공포 (SPoF)

```text
앱들 ──▶ MySQL 1대 ──💥──▶ 전체 정지 + (디스크까지 날가면) 자산 소실
```

교육 Day31이 말하는 출발점이다.  
주방이 멀쩡해도 장부 방이 하나면, 그 방 열쇠를 잃는 순간 가게가 멈춘다.

### 3.2 쓰기 확정과 무전기 (개념)

```text
Nest → Router:6446 → Primary:13306
         │
         │  “주문 INSERT”
         ▼
Primary가 변경 준비
         │
         │  GR :13361 로 “이 기록, 공식으로?”
         ▼
과반(쿼럼) 승인 → 커밋 확정
         │
         ▼
Secondary 사본 반영
```

| 용어 | 의미 |
|------|------|
| Primary | 읽기/쓰기 중심 노드 |
| Secondary | 복제·읽기·승격 후보 |
| Quorum | 보통 `(N/2)+1` → 3노드면 **2** |
| Failover | Primary 사망 시 새 Primary 선출 |

### 3.3 왜 하필 3대인가

| N | 과반 | 한 대 죽으면 |
|---|------|--------------|
| 1 | 1 | 끝 (SPoF) |
| 2 | 2 | 과반 깨지기 쉬움 / 스플릿 브레인에 취약 |
| **3** | **2** | **1대 장애**까지 과반 유지에 유리 |
| 5 | 3 | 더 견고, 비용·복잡도↑ |

AZ-a/b/c에 한 대씩 두면, **한 AZ 장애 ≈ 노드 1대 장애**로 맞춰 생각하기 좋다.

### 3.4 앱은 Primary IP를 외우지 않는다 — Router

페일오버 후 Primary IP가 바뀌면 Nest env를 전부 고칠 것인가?  
그래서 **MySQL Router**가 있다.

| 포트 | 역할 | Nest |
|------|------|------|
| **6446** | Read-Write | 1차 기본 (읽기/쓰기) |
| **6447** | Read-Only | 읽기 전용 분산 (선택) |

1차 Nest는 `127.0.0.1:6446`만 써도 “읽기/쓰기 하나” 그림과 맞는다.  
읽기를 Secondary로 나누고 싶으면 나중에 RO 포트·커넥션을 분리한다.

**Router 위치 (1차):** 앱 EC2 로컬 (집 안 안내원).  
`sg-router`는 만들어 두되 전용 EC2에는 아직 안 붙인다.

```text
Nest ── localhost:6446 ──▶ Router(같은 EC2)
                              │ sg-app → sg-db :13306
                              ▼
                           Cluster
```

## 4. 무엇을 쓰지 않는가 (범위)

### 4.1 RDS를 쓰지 않는다 — 그러나 존중한다

| RDS가 가려 주는 것 | 우리가 직접 보는 것 |
|--------------------|---------------------|
| Multi-AZ / 복제 | EC2 3 + GR |
| 엔드포인트 | Router 6446/6447 |
| 콘솔 스냅샷 | **cron + S3** (원칙) |
| 패치 버튼 | OS·MySQL 책임 |

실서비스에서 고객 자산을 지키려면 관리형을 **진지하게** 고르는 것이 맞다.  
이 프로젝트는 **원리를 이해하고 있음을 확인**하기 위한 학습 경로다.

### 4.2 Compose 안 MySQL / Swarm `my-db`를 쓰지 않는다

앱 ASG와 DB 수명을 묶으면, 인스턴스를 교체할 때마다 장부가 위태로워진다.  
로컬 Day32~33의 미니 냉장고와, 클라우드 지하 금고를 혼동하지 않는다.

### 4.3 DB에 ASG를 걸지 않는다

알바(앱)는 교대 가능.  
금고 이사회 의원 수를 Auto Scaling으로 줄이면 **쿼럼이 깨질 수 있다.**

## 5. 배치·포트·네트워크·보안 — 이미 깔아 둔 바닥

### 5.1 서브넷 (금고동)

| 노드 | CIDR | AZ |
|------|------|-----|
| db-a | `10.0.20.0/24` | ap-northeast-2a |
| db-b | `10.0.21.0/24` | ap-northeast-2b |
| db-c | `10.0.22.0/24` | ap-northeast-2c |

라우팅: **local only** + **S3 Gateway Endpoint**.  
`0.0.0.0/0 → NAT/IGW` **없음.**  
길이 없으면 실수로 도어락을 풀어도 바깥 산책이 어렵다.

### 5.2 포트 (`ports.tf` 고정)

| 포트 | 역할 | 비유 |
|------|------|------|
| **13306** | MySQL 클라이언트 창구 | 손님·Router |
| **13361** | Group Replication | 무전기. `13306×10+1=133061`은 TCP 상한 초과 → **수동 고정** |
| **33060** | X Protocol / Shell | 관리자 마스터키 |
| **6446 / 6447** | Router RW / RO | Nest가 외우는 번호 |

### 5.3 `sg-db` (이중 자물쇠의 두 번째)

| 방향 | 포트 | 상대 |
|------|------|------|
| In | 13306 | sg-app, sg-router, self |
| In | **13361** | **self (필수)** |
| In | 22 / 33060 | Bastion 등 |
| Out | 해당 포트 | **self만** (인터넷 egress 없음) |

GR은 노드가 **먼저** 말을 건다.  
Stateful SG에서 **ingress self만** 열고 egress를 잠그면 무전기 **송신**이 안 된다.  
**in + out 쌍**이 필요하다.

공인 IP를 DB에 달지 않는다. 관리는 **Bastion 경유만**.

## 6. 가장 중요한 두 가지 — 영속 저장과 백업

초안에서 강조한 문장을 설계 원칙으로 승격한다.

> 중요한 것은 **백업**과 **데이터 저장**이다.  
> 혹시나 EC2가 꺼지거나 사라져도 데이터가 날아가면 안 된다.  
> 데이터는 **볼륨 등**을 이용해 **영구적으로(인스턴스 수명과 분리해)** 저장해야 한다.  
> 또한 **crontab** 등으로 일정 시각에 백업하고,  
> **일정 기간이 지나면** 오래된 백업을 지워 비용을 통제할 수 있다.

이것이 “원리를 이해하고 있음”을 확인하는 핵심 과제다.  
클러스터만 띄우고 백업·볼륨을 빼먹으면, **HA 흉내만 낸 것**이다.

---

### 6.1 영속 저장 — 왜 EBS 볼륨인가

#### 문제

EC2의 **인스턴스 스토어**나, “루트 볼륨만 대충” 쓰면:

| 사건 | 데이터 |
|------|--------|
| `stop` / `start` | 설정에 따라 위험할 수 있음 |
| `terminate` | 루트만 쓰면 **장부까지 삭제**되기 쉬움 |
| OS 재설치 | datadir이 루트에 있으면 같이 날아감 |

비유:

> 장부를 **건물 벽지 뒤**에 숨기면, 리모델링할 때 장부도 뜯긴다.  
> 장부는 **옮길 수 있는 철제 캐비닛(EBS)** 에 넣어야 한다.

#### 설계 결정

| 볼륨 | 내용 | 수명 |
|------|------|------|
| **루트 볼륨** | Ubuntu, MySQL 패키지, 설정 | OS 교체 가능 |
| **데이터 볼륨 (권장·원칙)** | MySQL `datadir` | **인스턴스와 분리**. detach/attach 가능 |

```text
[EC2 db-a] ── / (루트)
           ── /var/lib/mysql  ← EBS 데이터 볼륨 마운트 (예시 경로)
```

각 노드(a/b/c)마다 **자기 데이터 볼륨**을 둔다.  
클러스터라고 해서 디스크 하나를 세 대가 동시에 쓰는 구조가 아니다.  
**각자가 사본을 들고**, GR로 내용을 맞춘다.

#### “영구”의 정확한 의미

클라우드에서 절대 영구는 없다.  
여기서 말하는 영구는:

> **EC2 프로세스/인스턴스 수명 ≠ 데이터 수명**  
> 인스턴스를 꺼도, 교체해도, **볼륨에 비트는 남길 수 있게** 설계한다.

스냅샷·다른 리전 복사까지가 진짜 DR이지만, 1차 설계의 최소선은 **데이터 볼륨 분리**다.

### 6.2 백업 — 클러스터가 대체하지 못하는 것

#### 클러스터 ≠ 백업

| 클러스터가 돕는 것 | 클러스터가 못 막는 것 |
|--------------------|------------------------|
| 노드 1대 다운 | `DROP DATABASE` / 잘못된 DELETE |
| AZ 1곳 장애 | 랜섬·악의적 삭제 |
| Primary 페일오버 | 세 노드에 동시에 적용된 잘못된 스키마 |

비유:

> 금고 칸을 세 개로 늘려도,  
> **세 칸 모두에 “장부 불태우기”를 동시에 명령하면** 끝이다.  
> 그때 필요한 것은 **어제 복사해 둔 서류**다.

그래서 Day29의 **RPO / RTO**를 설계에 남긴다.

| 지표 | 질문 | 1차 목표 예 |
|------|------|-------------|
| **RPO** | 최대 얼마나 과거로? | 매일 덤프 (+ 여유 되면 binlog) |
| **RTO** | 얼마나 빨리 되돌리나? | restore 런북 **1회 성공** |

#### 백업 경로

```text
[DB 노드]
   │  mysqldump / 백업 도구 (예시)
   │  cron 으로 매일 03:00 등
   ▼
로컬 임시 파일
   │
   │  aws s3 cp  (S3 Gateway Endpoint — NAT 없이)
   ▼
[S3 버킷]  backups/coupang-eats-dev/YYYY-MM-DD.sql.gz
   │
   │  수명 주기 (예: 7일 후 삭제 / Glacier 등)
   ▼
오래된 객체 만료
```

DB 서브넷 RT에 S3 Endpoint를 붙여 둔 이유가 여기 있다.  
금고가 담장 밖 길을 안 쓰면서도 **서류 창고(S3)** 에는 닿는다.

#### crontab으로 일정 백업 — 설계에 포함하는 이유

초안 그대로다.

| 할 일 | 왜 |
|------|-----|
| **cron으로 주기적 백업** | “기억나면 덤프”는 반드시 잊는다. 자산 보호는 **습관이 아니라 스케줄** |
| **S3에 보관** | 노드 디스크만의 백업은 노드·AZ 장애에 같이 죽을 수 있음 |
| **일정 기간 후 삭제** | 무한 보관 = 비용·개인정보 보관 기간 이슈. **보존 기간을 정하는 것**도 설계 |
| **수동 restore 1회** | 백업 파일만 쌓고 복원을 안 해 보면 “안심 파일”일 뿐 |

예시 정책 (숫자는 구현 편에서 확정 가능):

```text
주기:     매일 1회 (또는 실습 중에는 수동 + cron 골격)
보존:     7일 (이후 S3 Lifecycle로 삭제)
위치:     s3://…/mysql-backup/
검증:     월 1회 또는 구축 직후 1회 restore 리허설
```

비유:

> 매일 밤 장부 복사본을 은행 금고(S3)에 맡기고,  
> **일주일이 지난 복사본은 창고에서 폐기**한다.  
> “얼마나 남길지”를 정하지 않으면 창고 임대료가 자산을 잡아먹는다.

#### 백업이 “원리를 이해했는지”를 확인하는 이유

복제만 켜고 “이제 안전하다”고 말하면,  
실무에서 가장 비싼 착각을 배운 것이다.

우리는 의도적으로:

1. **볼륨으로 인스턴스와 데이터를 분리**하고  
2. **cron으로 시간축 복사본**을 만들고  
3. **보존·삭제 정책**까지 말로 고정한다  

이것이 RDS 콘솔의 “자동 백업·보존 기간” 버튼 뒤에서 일어나는 일을 **손으로 한 바퀴** 도는 훈련이다.

## 7. Nest(WAS)와의 연결

```text
DATABASE_HOST=127.0.0.1
DATABASE_PORT=6446          # Router RW = 읽기/쓰기 창구
DATABASE_USER=app_user
DATABASE_NAME=coupang_eats
PASSWORD → SSM / Secrets (Git·이미지 bake 금지)
```

| 금지 | 이유 |
|------|------|
| Primary IP 직접 | 페일오버 시 Nest가 깨짐 |
| 인터넷 공개 MySQL | 자산 유출 경로 |
| Compose에 mysql “임시” | 티어·수명 붕괴. 임시가 영구가 됨 |

성공 사다리:

```text
클러스터 ONLINE
 → Bastion에서 DB 접속
 → 앱에서 127.0.0.1:6446
 → 마이그레이션
 → DB API 200
 → (선택) Primary stop 후 Router 전환 확인
 → cron 백업 1회가 S3에 존재
```

## 8. AMI·인스턴스·시공 순서 (설계 수준)

### 8.1 초안

| 항목 | 1차 제안 |
|------|----------|
| AMI | Ubuntu 24.04 LTS |
| 타입 | t3.small ~ t3.medium (3대 비용 고려) |
| MySQL | 호스트 설치 (Day31 축). DB용 Docker는 1차 비권장 |
| 디스크 | 루트 + **데이터 EBS** |
| 키 | Bastion 경유 SSH |

### 8.2 시공 로드맵 (코드는 다음 편)

```text
[완료] 네트워크 DB 서브넷·RT·S3 EP / sg-db·ports
   ↓
① EC2×3 + 데이터 EBS 부착·마운트·datadir
② MySQL 설치·13306/13361/서버 UUID 등 설정
③ Bastion에서 InnoDB Cluster bootstrap
④ 앱 EC2에 Router → 6446
⑤ Nest 연결·스키마
⑥ cron 백업 스크립트 + S3 + Lifecycle(보존 기간)
⑦ restore 리허설 1회
⑧ (선택) Primary 장애 주입
```

Terraform이 서버·볼륨·SG를 만들고,  
클러스터 create 같은 **일회성 의식**은 Bastion + 문서화된 절차여도 된다.  
인프라와 데이터플레인의 경계를 인정한다.

### 8.3 apply 원칙

> 설계·코딩·`plan`까지.  
> **`apply` / `destroy`는 본인 승인 후에만.**  
> DB 3대 + EBS는 방치 시 청구서가 장부를 대신한다.

## 9. 장애·백업 시나리오로 기대값 고정

| 사건 | 기대 |
|------|------|
| Secondary 1대 다운 | 쓰기 유지 (과반) |
| Primary 다운 | 선출 + Router가 RW 전환. Nest는 6446 유지 |
| 앱 EC2 1대 다운 | ASG 교체. **DB 장부는 무관** |
| EC2 terminate (데이터 EBS 분리 시) | 볼륨은 남김 → 새 인스턴스에 attach 가능해야 함 |
| `DROP DATABASE` | 클러스터도 같이 삭제됨 → **S3 백업에서 restore** |
| 백업 7일 경과 | Lifecycle로 객체 삭제 (정책대로) |

## 12. 성공 기준 (최종)

**성공**

- [ ] 네트워크·SG·도메인·컴퓨팅에 이어 **DB 설계가 SSOT로 문서화**됨  
- [ ] EC2 3대 × 3AZ × private_db, Primary 1 + Secondary 2 역할이 명확  
- [ ] Nest는 Router `6446`만 보고 Primary IP를 하드코딩하지 않음  
- [ ] **데이터 EBS**로 인스턴스와 장부 수명 분리  
- [ ] **cron 백업 → S3**, **보존 기간 후 삭제** 정책이 설계에 존재  
- [ ] restore 절차를 최소 1회 검증할 계획  
- [ ] “실서비스는 RDS를 진지하게”와 “학습은 직접 구축”이 문서에서 분리됨  

**아직 실패가 아닌 것**

- Router 전용 EC2 없음  
- Redis·완벽한 DR·제로다운타임 미보장  
- RDS급 원클릭 패치 없음

## 13. 한 줄 요약

지금까지 네트워크·보안·도메인·컴퓨팅을 끝냈고, 남은 것은 **Database**다.  
우리는 **고객 데이터가 자산**임을 알기에 보안을 쌓았고,  
실서비스에서는 **RDS로 안전하게 운영하는 길**이 중요한 경우가 많다는 것도 인정한다.  
다만 이 프로젝트는 **원리를 확인하기 위해** RDS 대신 **EC2 3대 InnoDB Cluster**(읽기/쓰기 Primary 1 + 읽기 Secondary 2)를 직접 구축한다.  
꺼져도 장부가 남도록 **EBS 볼륨**에 영속하고, **cron + S3 + 보존 기간 삭제**로 백업 축을 설계에 포함한다.
