# [본편] VPC부터 쌓는 네트워크 — 서울 리전, /16 VPC, 9개 서브넷, IGW·NAT·S3 Gateway Endpoint

앞서 [밑바닥부터 다시 쌓는 3-Tier 인프라](./blog-ecs-less-3tier-intro.md)를 어떻게 구축할지에 대한 설계를 전체적으로 살펴보았다.  
본편에서는 **실제 구축**을 진행한다. 가장 먼저 손댈 것은 **네트워크**다. AWS에서 **VPC(나만의 사설망)** 를 설계하는 것부터, 이를 실제로 구현하기까지의 여정인 셈이다.

WEB(Nginx) · WAS(Nest on EC2+ALB+ASG) · DB(EC2 MySQL 클러스터)는 모두 이 VPC 안에서만 의미를 갖는다.  
집이 없는데 가전을 들이는 것과 같기 때문에, **인프라의 첫 커밋은 항상 네트워크**다.

---

## 0. 리전 선택 — 왜 서울(ap-northeast-2)인가

네트워크를 만들기 전에 리전을 고정한다. 이번 실습은 **서울 리전(ap-northeast-2)** 을 사용한다.

이유는 단순하다.

1. **서비스 사용자가 가장 많을 가능성이 높은 리전**이 서울이다. 지연 시간과 운영 감각 모두 실제 서비스에 가깝다.
2. 서울은 **가용 영역(AZ)이 복수**다(현재 기준 네 개 축). 그중 **세 AZ**에 자원을 나눠 두면, 단일 AZ 장애에도 버틸 수 있는 고가용성 뼈대를 만들기 좋다.

이번 설계에서는 AZ를 **세 개** 사용한다.  
(네 개 전부를 쓸 필요는 없다. 3-Tier HA 실습의 정석 패턴이 “퍼블릭 / 프라이빗 앱 / DB를 AZ마다 하나씩”이기 때문이다.)

---

## 1. VPC 하나, CIDR /16 — “왜 이렇게 쓰는지”

먼저 서울 리전에 **VPC를 하나** 만든다.  
지금은 **VPC 피어링·Transit Gateway 같은 VPC 간 연결은 필요 없다.** 쿠팡이츠 클론 인프라는 단일 VPC 안에서 완결해도 충분하다.

### 1.1 CIDR을 /16으로 주는 이유

VPC CIDR은 **`10.0.0.0/16`** 같은 형태로 둔다. (사설 대역이면 `10.0.0.0/16`, `172.16.0.0/16` 등. 실습에서는 `10.0.0.0/16`을 기준으로 설명한다.)

예전에 IP는 **클래스풀 서브네팅(A/B/C)** 으로 나뉘어 있었다.

| 클래스(옛 구분) | 대략적 규모 | 대표 마스크 감각 |
|-----------------|-------------|------------------|
| A | 초대형 | `/8` 근처 |
| B | 중형 | `/16` 근처 |
| C | 소형 | `/24` 근처 |

지금은 **CIDR(Classless)** 이 표준이라 “반드시 B 클래스여야 한다”는 규칙은 없다.  
다만 현장에서 VPC를 잡을 때 **`/16`을 VPC에 주고, 그 안을 `/24` 서브넷으로 쪼개는 패턴**이 가장 흔하고 읽기 쉽다.  
“중규모 사설망을 하나 잡고, 그 안을 256개 단위로 칸막이한다”는 감각이 클래스 B → 서브넷 C 단위와 잘 맞기 때문에, 교육·실무 모두에서 **정석처럼** 쓰인다.

### 1.2 `/16`과 `/24`가 의미하는 것

IP 주소는 32비트다. 흔히 점 네 개(`a.b.c.d`)로 쓰고, 각 칸은 0~255다.

- **`/16`:** 앞 **16비트**를 “우리 네트워크 고정”, 뒤 16비트를 호스트·서브넷에 사용하겠다는 뜻이다.  
  서브넷 마스크로 쓰면 **`255.255.0.0`** 에 해당한다.  
  VPC 전체로 보면 이론상 약 **65,536**개 주소 공간이 열린다.
- **`/24`:** 앞 **24비트**를 네트워크로 쓰겠다는 뜻이다.  
  마스크는 **`255.255.255.0`**.  
  한 서브넷에서 쓸 수 있는 주소는 **256개**(0~255) 블록이다.

AWS는 각 서브넷에서 **5개 주소를 예약**한다(네트워크 주소, VPC 라우터, DNS 등, 브로드캐스트 예약 등).  
그래서 `/24` 서브넷에서 실제로 EC2 등에 붙일 수 있는 건 **256 − 5 = 251개** 정도라고 기억하면 된다.

정리하면:

- VPC = **넓은 방(`/16`)**
- 서브넷 = **그 방을 `/24`로 나눈 칸**
- 칸마다 AZ를 정해 “물리적으로도 떨어뜨린다”

이 설계를 고른 이유는 “예뻐 보여서”가 아니라, **확장 여유(/16) + 운영 가독성(/24) + AWS 예약 주소까지 감안한 실무 습관**이기 때문이다.

## 2. 서브넷 9개 — 퍼블릭 3 · 프라이빗(앱) 3 · DB 3

하나의 VPC(`/16`) 안에, **가용 영역 3개**에 맞춰 서브넷을 만든다.

| 구분 | 개수 | 역할 |
|------|------|------|
| **퍼블릭 서브넷** | AZ당 1개 × 3 | ALB, Bastion, NAT Gateway 등 인터넷과 직접 닿을 수 있는 자원 |
| **프라이빗 서브넷 (앱)** | AZ당 1개 × 3 | WEB(Nginx) + WAS(Nest)가 올라갈 ASG EC2 |
| **DB 서브넷** | AZ당 1개 × 3 | MySQL 클러스터 노드 (인터넷 라우팅 없음) |

**총 9개 서브넷**이 필요하다.

예시 CIDR 배치(`10.0.0.0/16` 기준, 읽기 쉽게 번호를 나눈 것):

| 이름 | CIDR 예 | AZ |
|------|---------|-----|
| public-a | `10.0.0.0/24` | ap-northeast-2a |
| public-b | `10.0.1.0/24` | ap-northeast-2b |
| public-c | `10.0.2.0/24` | ap-northeast-2c |
| private-app-a | `10.0.10.0/24` | a |
| private-app-b | `10.0.11.0/24` | b |
| private-app-c | `10.0.12.0/24` | c |
| private-db-a | `10.0.20.0/24` | a |
| private-db-b | `10.0.21.0/24` | b |
| private-db-c | `10.0.22.0/24` | c |

번호 체계는 팀 취향이다. 중요한 것은 **퍼블릭 / 앱 프라이빗 / DB가 대역만 봐도 구분되게** 두는 것이다.

3-Tier와의 대응은 다음과 같다.

```text
퍼블릭 서브넷     → 입구(ALB), 관리(Bastion), NAT
프라이빗 앱 서브넷 → WEB + WAS (Nginx, Nest on ASG)
DB 서브넷         → DB 티어 (MySQL 클러스터)
```

## 3. 인터넷으로 나가는 길 — IGW, NAT, DB는 “길 없음”

서브넷은 “칸”일 뿐이고, **패킷이 어디로 갈지**는 **라우팅 테이블**이 정한다.  
라우팅 테이블은 “이 목적지면 이 게이트웨이(또는 local)로 보낸다”는 **미리 적어 둔 길 안내판**이다.

### 3.1 인터넷 게이트웨이(IGW) — 하나, 외부로 통하는 유일한 문

- VPC에 **IGW는 하나** 붙인다.
- 퍼블릭 서브넷의 라우팅 테이블에  
  `0.0.0.0/0 → igw-xxxx`  
  를 넣는다.
- 여기에 놓인 자원(ALB, 퍼블릭 IP를 가진 Bastion 등)만 **양방향 인터넷 경로**를 가질 수 있다.  
  (보안 그룹으로 포트를 막더라도, “경로” 자체는 IGW를 통해 열린다.)

IGW는 VPC당 하나면 충분하다. **외부로 통하는 유일한 L3 출입구**로 이해하면 된다.

### 3.2 NAT 게이트웨이 — 프라이빗 앱이 “나가기만” 하는 길

프라이빗 앱 서브넷의 EC2는 **퍼블릭 IP가 없다.**  
그래도 OS 업데이트, Docker Hub/ECR pull, 외부 API 호출이 필요할 수 있다.  
이때 쓰는 것이 **NAT Gateway**다.

동작 감각은 다음과 같다.

1. 프라이빗 인스턴스 → NAT(퍼블릭 서브넷에 위치)로 나감  
2. NAT가 **공유(탄력적) IP**로 바꿔 인터넷으로 보냄  
3. 응답이 돌아오면 NAT가 다시 **내부 IP**로 바꿔 원래 인스턴스에 전달  
4. **인터넷에서 먼저 프라이빗 IP로 들어오는 연결은 성립하지 않는다** (outbound 중심)

라우팅 예:

- 프라이빗 앱 RT: `0.0.0.0/0 → nat-xxxx`

**비용·HA 팁 (실습 시 의식할 것):**

- **학습·비용 절감:** NAT를 **1개**(한 AZ의 퍼블릭 서브넷)만 두고 세 앱 서브넷이 공유 → 저렴하지만 NAT AZ 장애 시 출구 SPOF.
- **운영에 가깝게:** AZ마다 NAT 1개 → 비용↑, AZ 장애에 강함.

이번 글의 원칙(“클라우드를 잘 다루되 밑바닥을 이해”)에서는, 처음엔 NAT 1개로 길을 연 뒤, 여유 있으면 Multi-AZ NAT로 올려도 된다. **설계 의도(프라이빗은 IGW에 직접 안 붙인다)는 동일**하다.

### 3.3 DB 서브넷 — 인터넷 라우팅을 넣지 않는다

DB 서브넷 라우팅 테이블에는 **`0.0.0.0/0` → IGW/NAT 를 넣지 않는다.**  
기본적으로 **VPC 내부(`local`) 통신만** 가능하게 둔다.

- WAS(프라이빗 앱) → DB : 보안 그룹으로 3306 허용  
- 인터넷 → DB : **경로도 없고, 열려서도 안 된다**  
- 관리자는 **Bastion(퍼블릭)** 으로 SSH한 뒤, 프라이빗으로 들어가거나 SSH 터널로 접근

이것이 “DB는 내부에서만 통신하게 만든다”는 말의 네트워크 층 구현이다.  
RDS Private Subnet Group과 같은 철학을, EC2 MySQL 클러스터에 손으로 재현하는 것이다.

### 3.4 기본(Default) 라우팅 테이블을 하나 더 두는 이유

메인 서브넷들은 **명시적 RT**에 연결한다.

- 퍼블릭 RT (IGW)
- 프라이빗 앱 RT (NAT)
- DB RT (local only)

여기에 더해, VPC 생성 시 생기는 **default route table**을 “아무데도 안 쓰이거나, 실수로 붙은 서브넷의 안전망”으로 남겨 두는 습관이 있다.  
예상치 못한 서브넷이 생기거나 나중에 붙일 자원이 있을 때, **기본값으로라도 어디로 흐를지**를 통제하기 위함이다.  
실습에서는 default RT에 IGW를 막 열어 두지 않고, **명시적으로 만든 RT만 서브넷에 associate** 하는 방식을 추천한다.

## 4. S3 게이트웨이 엔드포인트 — NAT 비용을 피하고, 내부로 S3에 간다

프라이빗 서브넷에서 S3에 가려면 원래 NAT → IGW → 공인터넷 → S3 경로를 탄다.  
**이미지·빌드 아티팩트·백업 파일**을 모두 S3에 둘 계획이면, 이 트래픽이 NAT 데이터 처리 비용으로 쌓이기 쉽다.

그래서 **S3 Gateway VPC Endpoint**를 만든다.

- 타입: **Gateway** (Interface가 아님. S3·DynamoDB용)
- 효과: 프라이빗 라우팅 테이블에  
  `pl-xxxx (S3 prefix list) → vpce-xxxx`  
  가 추가되어, **AWS 백본으로 S3에 붙는다**
- **Gateway Endpoint 자체 요금은 없고**, NAT를 거치지 않아 **NAT 데이터 비용을 크게 줄일 수 있다**

### 4.1 DynamoDB Gateway Endpoint는?

DynamoDB도 Gateway Endpoint를 만들 수 있지만, **이 프로젝트 런타임에서는 DynamoDB를 쓰지 않는다.**  
Terraform의 원격 state 잠금 등으로 DynamoDB를 쓸 수는 있으나, 그건 **로컬/CI가 AWS API로 붙는 이야기**에 가깝고, VPC 안 WAS가 DynamoDB에 상시 붙는 구조는 아니다.  
따라서 **지금은 DynamoDB 엔드포인트를 생략**한다.  
나중에 MSA로 확장하며 DynamoDB를 쓰게 되면 그때 붙이면 된다. 아쉬움은 잠시 접어 둔다.

### 4.2 퍼블릭 서브넷에도 S3 Endpoint가 필요한가?

퍼블릭은 IGW로 나가도 S3에 갈 수 있고, **NAT처럼 비용이 크게 붙지는 않는다.**  
그래도 퍼블릭 RT에도 S3 Gateway Endpoint를 연결하는 팀이 많다. 이유는 비용보다:

- **인터넷을 경유하지 않는 경로** (보안·정책적으로 깔끔)
- 동일 VPC 안에서 S3 접근 경로를 **일관되게** 유지

속도 차이는 체감이 작을 수 있지만, **“반드시 인터넷으로 나가서 S3에 간다”를 기본값으로 두지 않는 것**이 중요하다.  
특히 프라이빗 앱·DB 백업 경로에서는 **S3 Endpoint를 사실상 필수**로 본다.

이번 실습에서 S3에 올릴 것:

- 업로드 이미지·파일
- (선택) 배포 아티팩트
- DB 백업 덤프
- Terraform `tfstate` 백엔드 버킷 (state 보관). 앱이 DynamoDB를 안 써도, **state용 S3**는 흔히 쓴다.

## 5. 라우팅을 한눈에

```text
[퍼블릭 서브넷 RT]
  local           → VPC 내부
  0.0.0.0/0       → IGW
  S3 prefix list  → S3 Gateway Endpoint  (권장)

[프라이빗 앱 RT]
  local           → VPC 내부
  0.0.0.0/0       → NAT Gateway
  S3 prefix list  → S3 Gateway Endpoint  (필수에 가깝다)

[DB 서브넷 RT]
  local           → VPC 내부
  (인터넷 기본 라우트 없음)
  S3 prefix list  → S3 Gateway Endpoint  (백업을 S3로 직접 올릴 때 유용)
```

“패킷이 어디로 가느냐”가 곧 **티어의 경계**가 된다.  
DB에 IGW 라우트가 없는 순간, DB 티어는 네트워크 레벨에서 이미 격리된 것이다.

## 6. NACL — 서브넷 단위 보안 (지금은 얕게, 나중에 깊게)

네트워크(칸과 길)를 만들었으면, **서브넷 단위 방화벽인 NACL(Network ACL)** 을 짚고 넘어간다.

솔직히 말하면, NACL은 **아직 수업에서 깊게 다루기 전**이라면 무리하게 복잡한 규칙을 넣을 필요는 없다.  
실무에서도 많은 팀이 **NACL은 기본(또는 넓은 allow) + 실제 세밀한 제어는 보안 그룹(SG)** 에 맡긴다.

알아 둘 차이만 정리한다.

| | **NACL** | **보안 그룹(SG)** |
|--|----------|-------------------|
| 적용 위치 | 서브넷 | ENI(인스턴스 등) |
| 상태 | **Stateless** (응답도 규칙 필요) | **Stateful** (허용한 요청의 응답은 자동) |
| 규칙 | 번호 순, allow/deny | allow만 (기본 deny) |
| 실습 1차 | 기본 유지 또는 inbound/outbound allow | ALB→Nginx→WAS→DB **체이닝**에 집중 |

이번 본편 네트워크 단계의 권장:

1. NACL은 **커스텀으로 과하게 잠그지 않는다** (잘못하면 ephemeral 포트 때문에 “나가지만 응답이 안 옴” 함정).
2. 티어 간 허용은 **보안 그룹 체이닝**으로 명확히 한다. (이건 다음 편 또는 컴퓨트 편에서 상세히.)
3. NACL을 배우면 그때 “서브넷 경계의 안전망”으로 보강한다.

“크게 건드릴 건 없다”는 감각은, **1차 목표(길과 칸을 맞게 깐다)** 에서는 틀린 말이 아니다.  
다만 “NACL이 뭔지 모른다”로 끝내기보다, **SG가 主役이고 NACL은 보조**라는 위치만 기억해 두면 된다.

## 7. 이번 편에서 만드는 것 체크리스트 (구현 순서)

Terraform으로 옮길 때도 이 순서가 그대로 state의 의존 순서가 된다.

1. **리전** `ap-northeast-2` 고정  
2. **VPC** `10.0.0.0/16` (또는 선택한 /16)  
3. **서브넷 9개** (퍼블릭3 + 앱 프라이빗3 + DB3), 각 `/24`, AZ 분산  
4. **IGW** 1개 attach  
5. **NAT Gateway** (1개 또는 AZ당 1개) + EIP  
6. **라우팅 테이블**  
   - 퍼블릭 → IGW  
   - 앱 프라이빗 → NAT  
   - DB → local only  
   - default RT 정책 정리  
7. **S3 Gateway Endpoint** + (앱·DB·필요 시 퍼블릭) RT 연결  
8. **DynamoDB Endpoint는 생략**  
9. **NACL** 기본/단순 유지, 세부 잠금은 SG 편으로  

이 위에 ALB·ASG·Nginx·Nest·MySQL 클러스터가 올라간다.

---

## 8. 설계 한 줄 요약

- **서울 리전**, VPC **하나**, CIDR **`/16`**, 서브넷 **`/24` × 9** (퍼블릭·앱·DB × 3 AZ).  
- **IGW 하나**로 퍼블릭만 인터넷에 열고, **NAT**로 앱 프라이빗의 outbound만 허용하며, **DB는 인터넷 라우트 없음**.  
- **S3 Gateway Endpoint**로 프라이빗(및 가능하면 퍼블릭)에서 S3를 내부 경로로 사용해 NAT 비용·보안을 잡는다. DynamoDB Endpoint는 이번 앱 범위 밖.  
- **NACL은 1차에 과신하지 않고**, 서브넷 격리의 본진은 **라우팅 + 이후 보안 그룹**에 둔다.

네트워크는 화려하지 않지만, 여기서 빗나가면 이후 ALB health·Bastion·DB 클러스터·S3 업로드가 전부 “원인 불명”으로 보인다.

이 설계를 코드로 옮긴 파일 단위 해설은 [네트워크 Terraform 코드 해설](./blog-terraform-network-code.md)에 있다. 주소는 `cidrs.tf`, 조립은 `main.tf`, 시공은 `modules/network`다.

다음 공사 편부터는 이 VPC 위에 **보안 그룹 체이닝과 Bastion**, 그리고 **WEB/WAS용 ASG**를 올리며 3-Tier를 실제로 채우면 된다.
