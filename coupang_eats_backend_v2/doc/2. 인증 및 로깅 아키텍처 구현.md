
# 인증 및 로깅 아키텍처 구현

     

> **견고한 인증 및 로깅 아키텍처 구현** \>견고한 인증 및 로깅 설계와 운영 가능한(Operable) 서버 구축 프로젝트

## 📖 Introduction

이 프로젝트는 단순히 이커머스 개발을 한 것이 아닙니다. \*\*"실제 수십만 명의 유저 트래픽을 감당할 수 있는 서버란 무엇인가?"\*\*라는 질문에서 시작하여, 엔터프라이즈급 환경에서 필수적인 **보안(Security)**, **관측 가능성(Observability)**, \*\*확장성(Scalability)\*\*을 갖춘 Backend Core를 구축하는 데 집중했습니다.

stateless한 JWT의 보안 한계를 극복하기 위해 **Redis 기반의 이중 토큰 인증 시스템**을 설계하였고, 분산 환경에서의 디버깅을 위해 **CLS(Continuation-Local Storage) 기반의 구조화된 로깅 시스템**을 구현했습니다.

## ⭐ Key Technical Decisions (Architecture & Engineering)

단순한 기능 구현을 넘어, 시스템의 안정성과 유지보수성을 극대화하기 위해 내린 핵심 기술적 의사결정입니다.

### 1\. 🛡️ Security & Authentication Architecture

**"보안 사고를 원천 차단하는 이중 토큰 및 쿠키 기반 인증 전략"**

기존의 단순 JWT 방식(LocalStorage 저장, 단일 토큰)이 가진 보안 취약점(XSS, 탈취 시 대응 불가)을 해결하기 위해 금융권 수준의 보안 프로세스를 적용했습니다.

  * **HttpOnly Cookie & Secure:** \* **Problem:** Refresh Token을 브라우저의 LocalStorage나 JSON Body로 주고받을 경우 XSS(스크립트 탈취) 공격에 무방비합니다.
      * **Solution:** Refresh Token을 JavaScript가 접근할 수 없는 `HttpOnly` 쿠키에 담고, `Secure` 옵션을 통해 HTTPS 환경에서만 전송되도록 하여 XSS를 원천 차단했습니다.
  * **RTR (Refresh Token Rotation):**
      * **Strategy:** 토큰 갱신 요청 시마다 새로운 Access Token과 Refresh Token을 발급하고, 이전 Refresh Token은 즉시 폐기합니다. 만약 해커가 이전 토큰을 재사용하려 할 경우, 이를 탈취 시도로 간주하여 해당 유저의 모든 토큰 체인을 무효화합니다.
  * **Redis Blacklist Strategy:**
      * **Mechanism:** 로그아웃 시 남은 유효기간이 있는 Access Token을 Redis 블랙리스트에 등록(`TTL` 적용)하여, Stateless한 JWT의 한계인 "즉각적인 접근 차단 불가" 문제를 해결했습니다.
  * **DIP (Dependency Inversion Principle) 적용:**
      * `AuthService`가 특정 암호화 라이브러리(Bcrypt)에 강하게 결합되는 것을 막기 위해 `HashModule`을 분리하고 인터페이스(`IHashService`)에 의존하도록 설계했습니다. 이를 통해 추후 Argon2 등의 알고리즘으로 교체 시 비즈니스 로직 수정 없이 인프라 계층만 교체 가능합니다.

### 2\. 👁️ Observability & Logging System

**"분산 환경을 대비한 추적 가능한(Traceable) 구조화된 로깅"**

서버가 확장(Scale-out)되거나 비동기 로직이 복잡해질 때, "누가 보낸 요청에서 에러가 났는지" 파악하기 어려운 Node.js의 한계를 극복했습니다.

  * **CLS (Continuation-Local Storage) 도입:**
      * **Implementation:** `nestjs-cls`를 활용하여 요청 진입 시점부터 응답까지 유지되는 고유한 \*\*Trace ID(Request ID)\*\*를 생성했습니다. 이를 통해 Service, Repository, Guard 등 코드 어느 곳에서든 별도의 파라미터 전달 없이 현재 요청의 Context에 접근 가능합니다.
  * **Structured Logging (Winston):**
      * **Strategy:** 단순 텍스트 로그 대신 JSON 포맷의 구조화된 로그를 남깁니다. AWS CloudWatch 등에서 `{ requestId: "abc-123", userId: 5 }` 와 같이 특정 필드를 기준으로 쿼리할 수 있어 트러블슈팅 속도를 획기적으로 단축했습니다.
  * **Request Lifecycle Tracking:**
      * **Middleware:** 요청 시작과 종료(Finish) 시점을 기록하여 API 응답 속도와 상태 코드를 모니터링합니다.
      * **Log Level Separation:** 정상 로직은 `Info`, 보안 위협(블랙리스트 접근 등)은 `Warn`, 시스템 에러는 `Error`로 레벨을 분리하여 알림 정책을 세분화했습니다.

### 3\. 🏗️ Robust Error Handling

**"Interceptor에서 Filter로: 사각지대 없는 에러 처리"**

  * **Global Exception Filter:**
      * 기존 `Interceptor` 방식은 Guard(인증) 단계에서 발생하는 에러를 포착하지 못하는 사각지대가 존재했습니다. 이를 해결하기 위해 NestJS 라이프사이클 최상단에 `Global Exception Filter`를 배치하여 인증 에러부터 비즈니스 로직 에러까지 모든 예외를 중앙에서 통제합니다.
  * **Sensitive Data Masking:**
      * 로그인/회원가입 요청 시 발생한 에러 로그에 사용자의 비밀번호가 평문으로 남지 않도록, Filter 단계에서 민감 정보를 `******`로 마스킹 처리하여 개인정보 보호 규정을 준수합니다.
  * **Environment-Aware Response:**
      * 개발(Dev) 환경에서는 디버깅을 위해 Stack Trace를 노출하지만, 운영(Prod) 환경에서는 이를 숨기고 표준화된 에러 메시지만 반환하여 보안성을 높였습니다.

## 📂 Project Structure

**Domain-Driven Design(DDD)** 원칙을 일부 차용하여, 기술적 인프라를 담당하는 `Core` 모듈과 비즈니스 로직을 담당하는 `Feature` 모듈을 철저히 분리한 **Layered Architecture**입니다.

```plaintext
📦 src
 ┣ 📂 core                <-- [Infrastructure Layer] 공통 기능 및 기술적 기반
 ┃ ┣ 📂 cls               # Request Context 관리 (Trace ID)
 ┃ ┣ 📂 config            # 환경변수 및 전역 설정 관리
 ┃ ┣ 📂 database          # TypeORM 설정 및 Repository 패턴 추상화
 ┃ ┣ 📂 decorator         # @CurrentUser, @IsNullable 등 커스텀 데코레이터
 ┃ ┣ 📂 filter            # 전역 예외 처리 (Global Exception Filter)
 ┃ ┣ 📂 guard             # 인증/인가 가드 (JWT, Role)
 ┃ ┣ 📂 hash              # 암호화 모듈 (Bcrypt Dependency Inversion)
 ┃ ┣ 📂 jwt               # JWT 발급/검증 전략 (Strategy)
 ┃ ┣ 📂 logger            # Winston 기반 구조화된 로깅 모듈
 ┃ ┣ 📂 middleware        # HTTP 요청 로깅 미들웨어
 ┃ ┗ 📜 core.module.ts    # Core 모듈 통합 관리
 ┣ 📂 modules             <-- [Application Layer] 비즈니스 도메인
 ┃ ┣ 📂 auth              # 인증 도메인 (Sign-in/up, Token Refresh)
 ┃ ┗ 📂 user              # 사용자 도메인
 ┣ 📜 main.ts             # 앱 엔트리 포인트
 ┗ 📜 setNestApp.ts       # 전역 설정 분리 (Test 환경 공유)
```

## 🔍 Deep Dive: Request Lifecycle

이 프로젝트에서 **하나의 API 요청**이 처리되는 과정은 다음과 같이 설계되어 안정성을 보장합니다.

1.  **Request In (Middleware):** `RequestLoggerMiddleware`가 요청을 감지하고, `ClsMiddleware`가 고유한 **Trace ID**를 부여합니다.
2.  **Security Check (Guard):**
      * `JwtBlacklistGuard`: Redis를 조회하여 로그아웃된 토큰인지 확인합니다.
      * `AccessTokenGuard`: 토큰의 서명을 검증하고, 만료 여부를 체크합니다.
3.  **Validation (Pipe):** `ValidationPipe`가 DTO의 유효성을 검사합니다.
4.  **Business Logic (Service):**
      * `AuthService` 등에서 비즈니스 로직을 수행합니다.
      * 필요 시 `LoggerService`를 통해 Trace ID가 포함된 로그를 기록합니다.
5.  **Exception Handling (Filter):** 에러 발생 시 `ErrorFilter`가 포착하여 민감 정보를 마스킹하고, 표준화된 JSON 포맷으로 클라이언트에 응답합니다.
6.  **Response Out:** 미들웨어가 최종 응답 시간(Duration)을 계산하여 CloudWatch 포맷으로 로그를 전송합니다.
