# 📝 Refactoring & Business Logic Update Report

본 업데이트(`Refactor/Update-Logic`)는 서비스의 **데이터 정합성(Data Consistency)**, **보안(Security)**, **성능 최적화(Optimization)**를 강화하는 데 중점을 두었습니다.
단순한 기능 구현을 넘어, 운영 환경에서 발생할 수 있는 동시성 문제와 데이터 불일치 문제를 해결하고 비효율적인 DB 접근을 개선했습니다.

---

## 🚀 Key Changes (주요 변경 사항)

### 1. User Module: 프로필 수정 및 캐시 정합성 확보
- **기능:** 유저 이름 및 비밀번호 변경 기능 구현 (`PATCH /users/profile`)
- **캐시 전략 (Cache Invalidation):**
  - `UserService` 조회 메서드에 적용된 `@Cache`로 인한 **Stale Data(구 데이터)** 문제를 해결하기 위해, 정보 수정 직후 `cacheService.del()`을 호출하여 캐시를 즉시 무효화했습니다.
- **보안:** 비밀번호 변경 시 `HashService`를 통해 암호화하여 저장하며, 회원가입 시점과 동일한 **강력한 비밀번호 정책(정규식)**을 적용했습니다.

### 2. Review Module: DB 최적화 및 중복 방지
- **1주문 1리뷰 정책:** `createReview` 시 이미 해당 주문에 대한 리뷰가 존재하는지 검사하여 중복 작성을 원천 차단했습니다. (`ConflictException`)
- **DB 호출 최소화 (Optimization):**
  - **생성 시:** 주문(`Order`) 조회 시 식당(`Restaurant`) 정보를 `JOIN`하여, 불필요한 식당 조회 쿼리를 제거했습니다.
  - **수정 시:** 존재 여부 확인을 위한 단순 조회(`findOne`)를 제거하고, 관계 로드와 검증을 한 번의 쿼리로 처리했습니다.
- **Soft Delete:** 리뷰 삭제 시 물리적 삭제 대신 논리적 삭제를 적용하여 데이터 복구 가능성을 열어두었습니다.

### 3. Order Module: 치명적 버그 수정 (Critical Fix)
- **문제:** 기존 `findByIds` 메서드는 `relations` 옵션을 지원하지 않아, 메뉴의 옵션(`DishOptions`) 정보를 가져오지 못하는 문제가 있었습니다. 이로 인해 옵션 가격이 계산되지 않는 버그가 발생했습니다.
- **해결:** `findManyWithOmitNotJoinedProps` 메서드로 교체하고 `{ options: true }`를 명시하여 메뉴와 옵션 정보를 정확히 로드하도록 수정했습니다.

### 4. Dish & Restaurant Module: 소유권 검증 강화
- **Ownership Verification:** 단순히 ID로 리소스를 조회하는 것을 넘어, 요청한 유저(`User`)가 해당 식당이나 메뉴의 실소유주(`Owner`)인지 확인하는 로직을 서비스 계층에 강제했습니다.
- **DTO:** `PartialType`을 활용하여 유연한 수정이 가능하도록 DTO를 재설계했습니다.

## 🔍 Code Analysis (코드 상세 리뷰)

### A. User Service: 캐시 무효화 패턴
**File:** `src/modules/user/user.service.ts`

```typescript
async updateUser(userId: string, dto: UpdateUserDto): Promise<User> {
  // 1. 유저 조회
  const user = await this.userRepository.findByIdOrThrow(userId);

  // 2. 비밀번호 암호화 (Plain Text 저장 방지)
  if (dto.password) {
    user.password = await this.hashService.hash(dto.password);
  }

  // 3. DB 저장
  const updatedUser = await this.userRepository.save(user);

  // 4. [핵심] 캐시 무효화 (Cache Look-aside Update Strategy)
  // 수정이 일어난 즉시 Redis에서 해당 유저의 캐시를 삭제해야
  // 다음 getUser 호출 시 DB에서 최신 데이터를 가져옵니다.
  await this.cacheService.del(`${CacheKeys.User}${userId}`);

  return updatedUser;
}
```

}
