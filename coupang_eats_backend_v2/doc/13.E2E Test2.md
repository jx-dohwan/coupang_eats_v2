

# 🛡️ E2E Testing & Backend Architecture Refactoring Report

본 문서는 **Coupang Eats V2** 프로젝트의 백엔드 시스템 구축 과정에서 진행된 **E2E(End-to-End) 테스트**와 그 과정에서 발견된 **아키텍처적 결함 보완 및 고도화** 내용을 상세히 기록합니다. 단순히 기능을 검증하는 것을 넘어, 데이터의 무결성, 시스템의 확장성, 성능 최적화를 위해 적용된 기술적 결정들을 포함합니다.

---

## 1. 선언적 트랜잭션 관리의 혁신 (`typeorm-transactional`)

### 🔍 도전 과제 (Challenge)

기존의 `dataSource.transaction(async manager => { ... })` 방식은 다음과 같은 치명적인 단점이 있었습니다.

* **코드 복잡도:** 비즈니스 로직마다 트랜잭션 코드가 침투하여 가독성이 저하됨.
* **리포지토리 주입 문제:** 트랜잭션 내에서 작업을 수행하려면 반드시 `manager.withRepository()`를 통해 리포지토리를 다시 획득해야 하며, 이를 누락할 경우 트랜잭션 외부에서 쿼리가 실행되는 위험이 존재함.
* **테스트 격리 실패:** 비동기 환경인 테스트 모듈에서 트랜잭션 컨텍스트가 전파되지 않아 롤백이 정상적으로 작동하지 않음.

### 💡 해결책 (Solution)

**AOP(관점 지향 프로그래밍)**를 활용한 **선언적 트랜잭션(`typeorm-transactional`)**을 도입했습니다.

* **원리:** `@Transactional()` 데코레이터를 사용하여 메서드 단위로 트랜잭션을 제어합니다. 이는 Proxy 패턴을 통해 런타임에 트랜잭션 시작/커밋/롤백 로직을 주입합니다.
* **CLS(Continuation Local Storage) 기반 컨텍스트 유지:** 비동기 호출 체인 내에서도 동일한 DB 연결 세션을 유지하도록 설정하여 서비스 간의 원자성(Atomicity)을 완벽히 보장합니다.
* **Side-Effect 안정성:** `runOnTransactionCommit()` 헬퍼를 도입하여, DB 작업이 완전히 성공한 시점에만 Socket.io 알림이나 AWS SES 이메일 발송이 이루어지도록 설계했습니다. 이는 DB는 저장되었으나 외부 API 호출 실패로 인해 전체 로직이 롤백되는 현상이나, 그 반대의 데이터 불일치 현상을 원천 차단합니다.

## 2. 커스텀 리포지토리 "Empty Shell" 현상 해결

### 🔍 도전 과제 (Challenge)

NestJS에서 커스텀 리포지토리를 주입받아 사용할 때, 클래스 내부에 `manager`나 `metadata` 속성이 `undefined`가 되어 실제 DB 접근 시 에러가 발생하는 '빈 껍데기' 현상이 발생했습니다.

### 💡 원인 분석 및 해결 (Root Cause & Fix)

* **원인:** `providers: [UserRepository]` 처럼 리포지토리를 직접 등록하면, NestJS DI 컨테이너는 TypeORM과의 연동 설정(DataSource 연결)이 누락된 순수 클래스 인스턴스를 생성해버립니다.
* **해결 (Dynamic Module Pattern):** `TypeOrmExModule`을 구축하여 리포지토리 주입 방식을 개선했습니다.
* **Factory 패턴 적용:** `useFactory`를 통해 `DataSource`로부터 해당 엔티티의 진짜 메타데이터를 가진 기본 리포지토리를 먼저 가져옵니다.
* **Constructor Injection:** 가져온 기본 리포지토리의 정보를 커스텀 리포지토리 생성자에 수동으로 주입하여, TypeORM의 기본 기능과 커스텀 비즈니스 메서드가 통합된 싱글톤 인스턴스를 보장합니다.

## 3. 엔티티 설계의 정교화 및 ORM 매핑 최적화

### 🔍 도전 과제 (Challenge)

JS 객체의 `camelCase`와 DB의 `snake_case` 간의 명칭 불일치로 인한 쿼리 에러와, 기획상 누락된 데이터 관계성으로 인해 비즈니스 로직 구현에 제약이 발생했습니다.

### 💡 해결책 (Solution)

1. **명시적 네이밍 전략:** 모든 외래키(FK) 컬럼에 `@Column({ name: 'snake_case' })`와 `@JoinColumn`을 명시하여 **임피던스 불일치(Impedance Mismatch)**를 해결했습니다.
2. **비즈니스 제약 조건의 DB화 (Review-Order):** "1주문 1리뷰" 정책을 위해 기획서에는 없던 `order_id`를 `ReviewEntity`에 추가하고 `OneToOne` 관계를 설정했습니다. 이를 통해 DB 레벨에서 중복 리뷰를 원천 차단했습니다.
3. **JSON 컬럼의 전략적 활용:** `Dish` 엔티티의 `options`를 별도 테이블이 아닌 **JSON 타입 컬럼**으로 설계했습니다. 이는 조인 비용을 줄이고, 변화가 잦은 메뉴 옵션 구조에 유연하게 대응하기 위함입니다.
* **주의:** JSON 컬럼은 `relations` 옵션에 넣으면 안 된다는 TypeORM의 원리를 테스트 과정에서 재확인하고 코드를 최적화했습니다.

## 4. 고성능 서비스 레이어 아키텍처 패턴

### 🔍 도전 과제 (Challenge)

다수의 주문 아이템(`OrderItem`)을 생성할 때 루프를 돌며 개별적으로 `save()`를 호출하는 방식은 대규모 트래픽 발생 시 DB 커넥션 고갈과 네트워크 오버헤드를 유발합니다.

### 💡 해결책 (Solution)

**메모리 수집 후 일괄 저장(Cascade Save)** 전략을 적용했습니다.

* **Memory-First Logic:** 반복문 내부에서는 `repository.create()`를 통해 엔티티 **인스턴스만 생성**하여 배열에 담습니다. (DB I/O 발생 0번)
* **Single Query Commit:** 부모 엔티티인 `Order`를 저장할 때 `@OneToMany(..., { cascade: true })` 설정을 통해 단 한 번의 `save()` 호출로 수십 개의 주문 항목을 하나의 쿼리로 삽입(Bulk Insert)합니다.
* **정밀 계산 검증:** 배달비(`deliveryFee`)와 옵션 금액이 합산되는 로직을 E2E 테스트를 통해 1원 단위까지 정합성을 맞췄습니다.

## 5. 격리되고 신뢰할 수 있는 E2E 테스트 환경

### 🔍 도전 과제 (Challenge)

테스트 실행 시 이전 테스트가 남긴 데이터(예: 중복된 이메일)로 인해 다음 테스트가 실패하거나, 실제 AWS 인프라 비용이 발생하는 등의 환경적 제약이 있었습니다.

### 💡 해결책 (Solution)

1. **전역 DB 초기화 유틸리티 (`dbCleanup`):**
* `SET FOREIGN_KEY_CHECKS = 0;` 명령을 선행하여 외래키 제약에 얽매이지 않고 모든 테이블을 비웁니다.
* `TRUNCATE` 명령을 사용하여 `DELETE`보다 빠르게 초기화하며, 자동 증가(ID) 값도 1로 리셋합니다.


2. **인프라 모킹 (Mocking):** `AwsS3Service`, `AwsSesService`를 인터페이스 기반의 Mock 클래스로 대체하여, 실제 네트워크 호출 없이 비즈니스 로직의 성공/실패 여부만 빠르게 검증합니다.
3. **Setup 공통화:** `createTestApp` 유틸리티를 통해 실제 앱(`main.ts`)과 동일한 `GlobalPipes`, `Interceptors`, `Guards` 환경에서 테스트가 진행되도록 보장했습니다.

## 🧠 기술 성과 요약 (Technical Summary)

| 구분 | 적용 기술 | 효과 및 이점 |
| --- | --- | --- |
| **트랜잭션** | `@Transactional` (Proxy Pattern) | 비즈니스 로직 원자성 확보, 코드 가독성 200% 향상 |
| **DI/모듈** | `TypeOrmExModule` (Dynamic Module) | 커스텀 리포지토리의 타입 안정성 및 싱글톤 보장 |
| **ORM 최적화** | JSON Column & Cascade Save | DB 부하 감소, 네트워크 오버헤드 최소화 |
| **데이터 무결성** | `runOnTransactionCommit` | DB와 외부 서비스(Email/Socket) 간 데이터 정합성 보장 |
| **테스트 품질** | `dbCleanup` & 격리된 테스트 슈트 | 기능 추가 시 즉각적인 회귀 테스트 가능 환경 구축 |
