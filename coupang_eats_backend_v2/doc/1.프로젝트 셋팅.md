# 🏗️ Base Architecture & Setup

이 프로젝트는 **Nest.js**를 기반으로 하며, 개발 효율성과 안정성을 위해 **Docker, Type-Safe Configuration, Custom TypeORM Repository** 등이 초기 설정되어 있습니다.

배포(ECS Fargate) 시 ALB는 **`GET /health`** 를 검사합니다. 로컬에서도 `http://localhost:3000/health` 로 확인할 수 있습니다.

## 1\. 로컬 개발 환경 (Docker)

로컬 개발 시 DB(MySQL)와 캐시(Redis) 환경을 통일하기 위해 `docker-compose`를 사용합니다.

### 🐳 실행 명령어

`package.json`에 정의된 스크립트를 통해 간편하게 제어할 수 있습니다.

```bash
# 컨테이너 실행 (백그라운드)
npm run docker:up

# 컨테이너 중지 및 제거
npm run docker:down
```

### ⚙️ 컨테이너 구성

| 서비스명 | 컨테이너명 | 포트 | 용도 |
| :--- | :--- | :--- | :--- |
| **mysql-dev** | `local-mysql-dev` | `3306` | 메인 개발용 데이터베이스 |
| **mysql-test** | `local-mysql-test` | `3307` | E2E 테스트용 독립 DB (데이터 오염 방지) |
| **redis** | `local-redis` | `6379` | 세션 관리 및 캐싱 |

## 2\. 환경 변수 (Configuration)

`process.env`를 직접 호출하지 않고, 주입받은 Service를 통해 설정값을 가져옵니다.

## 3\. Core Architecture: GenericTypeOrmRepository

이 프로젝트의 가장 핵심적인 아키텍처 요소입니다.
TypeORM의 기본 `Repository`를 상속받은 `GenericTypeOrmRepository`를 구현하여 \*\*타입 안정성(Type Safety)\*\*과 **에러 처리 자동화**를 제공합니다.

### 💎 왜 사용하는가?

1.  **Strict Type Safety**: `relations` 옵션에 명시하지 않은 관계 데이터에 접근하면 **컴파일 에러**가 발생합니다. (런타임 `undefined` 오류 방지)
2.  **Auto 404 Handling**: `...OrThrow` 메서드는 데이터가 없으면 자동으로 `NotFoundException`을 던집니다. 반복적인 `if (!data)` 검사가 필요 없습니다.

### 📚 메서드 가이드

#### 1️⃣ 관계(Join)가 필요한 조회

`findOptionsRelations`에 정의된 관계만 반환 타입에 포함됩니다.

| 메서드명 | 리턴 타입 | 설명 |
| :--- | :--- | :--- |
| **`findOneWithOmitNotJoinedProps`** | `T \| null` | 조건에 맞는 단일 엔티티 조회.<br>명시하지 않은 관계 필드는 타입에서 **제거됨**. |
| **`findOneWithOmitNotJoinedPropsOrThrow`** | `T` | 위와 동일하나, 데이터가 없으면 **404 예외** 발생.<br>리턴 타입에 `null`이 없음. |
| **`findManyWithOmitNotJoinedProps`** | `T[]` | 조건에 맞는 여러 엔티티 조회.<br>관계 필드 타입 안전성 보장. |

#### 2️⃣ 단일 테이블 조회 (No Relations)

관계(Join) 없이 해당 엔티티의 컬럼만 조회할 때 사용합니다.

| 메서드명 | 설명 |
| :--- | :--- |
| **`findByIdOrThrow(id)`** | PK(ID)로 조회. 실패 시 404 예외 발생. |
| **`findOneOrThrow(filters)`** | 필터 조건으로 조회. 실패 시 실패한 조건 목록과 함께 404 예외 발생. |
| **`findOneByFilters(filters)`** | 조건 조회 후 결과가 없으면 `null` 반환. |
| **`findMany(filters)`** | 조건에 맞는 엔티티 배열 반환 (관계 속성 접근 불가). |

### 💻 사용 예시 (Code Snippet)

```typescript
// ✅ Good Case: Generic Repository 사용
async getUserInfo(userId: string) {
  // 1. 데이터가 없으면 알아서 404 에러를 던짐 (try-catch 불필요)
  // 2. relations에 'profile'을 명시했으므로 profile 속성 접근 가능
  const user = await this.userRepo.findOneWithOmitNotJoinedPropsOrThrow(
    { id: userId },
    { profile: true } 
  );
  
  return user.profile.nickname; // 타입 안전하게 접근 가능
}

// ❌ Bad Case: 컴파일 에러 발생 상황
async getUserInfo(userId: string) {
  const user = await this.userRepo.findOneWithOmitNotJoinedPropsOrThrow(
    { id: userId },
    {} // relations 없음
  );
  
  // ⛔️ Compile Error: Property 'profile' does not exist on type...
  console.log(user.profile.nickname); 
}
```

## 4\. 응답 및 에러 처리 (Interceptors)

모든 API 응답은 **Interceptors**를 통해 표준화된 포맷으로 클라이언트에 전달됩니다.

### 🟢 성공 응답 (`ApiResponseInterceptor`)

Controller에서 데이터 객체만 리턴하면 자동으로 아래 구조로 래핑됩니다.

```json
{
  "success": true,
  "data": {
    "id": "uuid...",
    "email": "test@example.com"
  }
}
```

### 🔴 에러 응답 (`ErrorInterceptor`)

예외 발생 시 HTTP 상태 코드와 함께 일관된 에러 메시지를 반환합니다.

```json
{
  "success": false,
  "message": "User not found"
}
```

```bash
src/
├── common/             # 전역 유틸리티, 공통 타입
├── core/               # 핵심 인프라 (Config, DB, Interceptors)
│   ├── config/         # 환경변수 관리 (MoinConfigService)
│   ├── database/       # TypeORM 설정, GenericRepository, Seeds
│   └── interceptor/    # 응답 표준화
├── modules/            # 비즈니스 도메인 모듈 (Users, Auth 등)
├── app.module.ts
└── main.ts
```
