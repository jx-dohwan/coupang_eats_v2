## 📚 [Phase 5] API Documentation (Advanced Swagger Pattern)

프론트엔드 개발자와의 원활한 협업과 API 테스트 자동화를 위해 **NestJS Swagger (OpenAPI 3.0)**를 도입했습니다. 단순한 라이브러리 적용을 넘어, **생산성(Productivity)**과 **표준화(Standardization)**를 위해 **고급 문서화 패턴**을 설계하고 적용했습니다.

### 1. 설계 철학 및 아키텍처 (Architecture & Design)

#### 🛠️ Custom Decorator Pattern (커스텀 데코레이터)
Swagger 적용 시 발생하는 `Controller` 코드의 비대화(Boilerplate) 문제를 해결하기 위해, 자주 사용되는 응답 패턴을 **추상화**했습니다.

* **Problem**: 모든 엔드포인트마다 `@ApiOperation`, `@ApiResponse(200)`, `@ApiResponse(400)`, `@ApiBearerAuth` 등을 반복 작성하여 비즈니스 로직의 가독성이 저하됨.
* **Solution**: `ApiDocOk`, `ApiDocCreated` 등의 커스텀 데코레이터를 제작하여 **선언적(Declarative)**으로 작성하도록 개선.

| 기능 | 데코레이터 | 포함된 속성 |
| :--- | :--- | :--- |
| **조회 (GET)** | `@ApiDocOk` | `ApiOperation`, `ApiOkResponse`, `ErrorResponse(400, 500)` |
| **생성/수정** | `@ApiDocCreated` | `ApiOperation`, `ApiCreatedResponse`, `ApiBearerAuth`, `ErrorResponse(400, 401, 403)` |

**[Code Comparison]**
```typescript
// ❌ [Before] Standard Swagger (코드가 길고 지저분함)
@Post()
@ApiOperation({ summary: '생성' })
@ApiBearerAuth('access-token')
@ApiResponse({ status: 201, description: '성공', type: CreateOutput })
@ApiResponse({ status: 400, description: '실패' })
@ApiResponse({ status: 401, description: '인증 실패' })
create() { ... }

// ✅ [After] Custom Pattern (직관적이고 간결함)
@ApiDocCreated('생성', CreateOutput)
create() { ... }
```

### 2. 응답 규격 표준화 (Response Standardization)

모든 API 응답은 일관된 포맷을 따르도록 **Base DTO**를 상속받아 구현했습니다. 이를 통해 프론트엔드에서의 예외 처리 및 데이터 파싱 로직을 통일했습니다.

#### 📦 Base DTOs
* **`CoreOutput`**: 모든 응답 객체의 부모 클래스. 성공 여부(`ok`)와 에러 메시지(`error`) 필드를 기본 보장합니다.
* **`ErrorResponse`**: 예외 발생 시 반환되는 표준 에러 객체 명세입니다. (`statusCode`, `message`, `path`, `timestamp`)
* **`PaginationResponse<T>`**: 리스트 조회 시 메타데이터(`total`, `totalPages`, `hasNext`)와 데이터(`data`)를 포함하는 표준 구조입니다.

### 3. 고급 기술 구현 (Advanced Implementations)

Swagger의 한계를 극복하고 복잡한 데이터를 표현하기 위한 기술적 해결책들입니다.

#### 🧬 제네릭 타입(Generic) 문서화 해결
NestJS Swagger는 기본적으로 제네릭(`T`) 타입을 인식하지 못하는 한계가 있습니다. 이를 해결하기 위해 **상속과 `declare` 키워드**를 활용한 패턴을 적용했습니다.

* **Challenge**: `PaginationResponseDto<Restaurant>` 형태로 반환 시, Swagger UI에서 `data` 필드의 타입이 제대로 표시되지 않음.
* **Solution**: 각 도메인별로 구체화된 응답 클래스를 생성하고 `declare`로 타입을 명시.

```typescript
// Generic Wrapper Pattern
export class RestaurantPaginationResponse extends PaginationResponseDto<RestaurantEntity> {
  @ApiProperty({ type: [RestaurantEntity] })
  declare data: RestaurantEntity[]; // Explicit Type Declaration with 'declare'
}
```

#### 📝 복잡한 데이터 구조(JSON/Nested) 시각화
단순한 Primitive 타입뿐만 아니라, **JSON 객체 배열**이나 **중첩된 객체**도 Swagger UI에서 명확히 보이도록 처리했습니다.

* **Dish Options**: `Dish` 엔티티의 `options` 필드(JSON) 내부 구조를 보여주기 위해, 별도의 DTO 클래스(`DishOptionDto`)를 분리하고 `@ApiProperty({ type: [Class] })`를 적용하여 문서화했습니다.

### 4. API Documentation Access

서버 실행 후 아래 주소에서 인터랙티브한 API 문서를 확인할 수 있습니다.

* **URL**: `http://localhost:3000/api-docs`
* **Features**:
    * **Auth**: JWT 토큰 발급 및 갱신 프로세스
    * **User**: 프로필 관리 및 역할(Role) 확인
    * **Restaurant**: 식당 CRUD 및 페이지네이션 조회 (Generic Response)
    * **Order**: 주문 생성(Transaction), 상태 변경(Enum), 상세 조회
    * **Payment/Review**: 결제 검증 및 리뷰 작성 자격 제어
