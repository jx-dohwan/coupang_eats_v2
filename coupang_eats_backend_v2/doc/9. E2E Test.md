## 🧪 E2E Testing (End-to-End)

이 프로젝트는 서비스의 핵심 비즈니스 로직 안정성을 보장하기 위해 **Jest**와 **Supertest**를 활용한 E2E 테스트를 수행합니다.
단순한 API 호출 테스트를 넘어, 실제 데이터베이스(MySQL)와 연동하여 **사용자 시나리오(User Scenario)** 기반의 통합 흐름을 검증합니다.

### 📋 Testing Strategy (테스트 상세 설계 및 전략)

본 프로젝트의 E2E 테스트는 다음과 같은 기술적 특징과 설계 철학을 바탕으로 구현되었습니다.

#### 1. 독립된 테스트 환경 (Isolated Environment)
- **목표:** 로컬 개발 DB와 테스트 DB가 혼재되어 데이터가 오염되는 것을 방지합니다.
- **구현:** `jest-setup.ts`를 통해 테스트 실행 시 메모리상에서 환경변수를 강제로 주입, **Docker Test DB (Port 3307)**를 바라보도록 격리했습니다.
- **효과:** 개발자는 로컬 `.env` 설정을 신경 쓸 필요 없이, 언제나 깨끗한 환경에서 테스트를 수행할 수 있습니다.

#### 2. Stateful 시나리오 테스트 (Scenario-Based Testing)
단일 API를 독립적으로 테스트하는 것이 아니라, **실제 유저의 행동 흐름(Context)**을 유지하며 테스트합니다.
- **Flow:** 회원가입 → 로그인(JWT 획득) → 가게 등록(점주 권한) → 메뉴 추가 → 주문(고객 권한) → 배달 완료(DB 조작) → 리뷰 작성
- 앞 단계의 결과물(Token, ID)을 변수에 저장하여 다음 단계의 입력값으로 사용하는 **Stateful** 방식을 채택했습니다.

#### 3. 왜 통합 테스트(Integration Test)보다 E2E를 우선했는가?
- **효율성(ROI):** 현재 프로젝트 단계에서는 개별 Service 모듈을 격리하여 테스트하는 것보다, **전체 시스템의 유기적인 연결(Controller ↔ Service ↔ DB)**이 정상 작동하는지 확인하는 것이 우선순위가 높다고 판단했습니다.
- **커버리지:** NestJS의 E2E 테스트는 사실상 **광범위한 통합 테스트**의 역할을 겸하고 있습니다. `Supertest`를 통해 HTTP 요청부터 DB 저장까지의 전 과정을 검증하므로, 비즈니스 로직의 정합성을 가장 확실하게 보장합니다.

### 🔥 Troubleshooting & Technical Decisions (트러블슈팅 및 기술적 의사결정)

E2E 테스트 구축 과정에서 발생한 주요 이슈와 해결 방법입니다.

#### 1. Global Interceptor로 인한 응답 구조 불일치 해결
- **문제:** 서버의 `Global Interceptor`가 응답을 `{ data: ... }` 형태로 감싸는 반면, 테스트 코드는 원본 객체를 기대하여 `undefined` 에러 발생.
- **해결:** 응답 객체의 구조(Pagination 유무, Wrapping 유무)를 동적으로 파악하여 데이터를 추출하는 헬퍼 함수 `getBody(res)`를 구현하여 테스트 유연성을 확보했습니다.

#### 2. DTO Validation과 Query Parameter 타입 이슈
- **문제:** `GET /restaurants?limit=10` 요청 시, HTTP는 모든 Query를 string으로 보내지만 백엔드 DTO는 `number`를 기대하여 `400 Bad Request` 발생.
- **해결:** 테스트 환경의 `ValidationPipe` 옵션에 `transformOptions: { enableImplicitConversion: true }`를 추가하여 자동 형변환을 적용했습니다.

#### 3. 복잡한 비즈니스 상태 강제 변경 (Raw SQL 활용)
- **문제:** 리뷰(Review) 작성은 '배달 완료(Delivered)' 상태에서만 가능하나, 결제 로직(PG사 연동)을 테스트 환경에서 수행하기 어려움.
- **해결:** `DataSource`를 주입받아 **Raw SQL Query**를 통해 DB 상태를 강제로 변경하는 방식을 사용했습니다. 이때 MySQL 예약어인 `order` 테이블 충돌 문제를 백틱(`` `order` ``) 처리로 해결했습니다.
  ```typescript
  // 테스트 중 상태 강제 변경 예시
  await dataSource.query(`UPDATE \`order\` SET status = 'Delivered' WHERE id = '${orderId}'`);
  ```

#### 4. 페이지네이션 응답 구조 처리
- **문제:** `GET /restaurants` 요청 시 배열(`[]`)을 기대했으나, 실제로는 `{ data: { list: [], total: ... } }` 형태의 객체가 반환되어 `undefined` 에러 발생.
- **해결:** 디버깅 로그(`console.log`)를 통해 실제 응답 구조를 파악하고, `responseData.list`를 참조하도록 테스트 코드를 수정하여 해결했습니다.

### 🛠 How to Run Tests

테스트를 실행하기 위해서는 Docker 컨테이너가 실행 중이어야 합니다.

**1. 테스트 환경 실행 (Docker)**
```bash
# docker-compose.yml에 정의된 test-db(3307 포트) 실행
docker-compose up -d
```

**2. E2E 테스트 실행**
```bash
# 환경변수 주입 및 테스트 실행
npm run test:e2e

# 상세 로그 확인 (디버깅 모드)
npm run test:e2e -- --verbose
```
